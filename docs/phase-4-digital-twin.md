## 1. PHASE OBJECTIVE & CORE RESPONSIBILITIES
Build the Digital Twin Engine that maintains a dynamic, virtual representation of the climate over the pilot region. 

Unlike the forecasting engine (Phase 3) which only predicts variables, the Digital Twin Engine is the **central source of truth** that manages and synchronizes:
* Current observed climate state.
* Historical climate state.
* Forecasted climate state.
* Simulated/Scenario climate state.

**Core Responsibilities:**
* Create and manage climate entities (grid cells/districts).
* Track state transitions using strict, immutable versioning.
* Store historical snapshots and load prediction/simulation updates.
* Expose standardized APIs for downstream consumption.
* Publish system-wide events upon state changes.

## 3. ENTITY MODEL & STATE TYPES

### A. The Digital Twin Entity

Every monitored location (grid cell or district) is a dynamic object containing:

* **Attributes:** `Location ID`, `Latitude`, `Longitude`, `District`, `Timestamp`, `Rainfall`, `Maximum Temperature`, `Minimum Temperature`, `Climate Risk Score`, `Prediction Confidence`, `Scenario ID`, `Data Source`.
* **Methods:** `update_state()`, `load_history()`, `forecast()`, `simulate()`, `serialize()`.
* *Constraint:* No downstream component may directly modify stored states; all changes must route through entity methods.

### B. State Definitions

* **Current State:** Derived directly from authoritative observations (IMD/INSAT).
* **Historical State:** Immutable archive used for trend analysis, model validation, and RAG retrieval.
* **Forecast State:** Generated by Phase 3 outputs (includes predictions and confidence scores).
* **Scenario State:** Generated by future Phase 6 simulations (e.g., Temp +2°C, Rain -20%).

## 4. STORAGE, VERSIONING & EVENT SYSTEM

**State Versioning Constraints:**

* Each update creates a **new immutable version**. State must **NEVER** be overwritten.
* *Flow:* V1 (Observation) → V2 (Forecast Applied) → V3 (Scenario Applied) → V4 (New Observation).

**Storage Layer Constraints:**

* **Recommended Engines:** PostgreSQL, DuckDB, or Parquet files.
* The repository layer must be completely decoupled so the storage backend can be swapped seamlessly.

**Event System:**
Publish the following events for future modules to subscribe to:

* `Observation Updated`
* `Forecast Generated`
* `Scenario Applied`
* `Risk Updated`
* `Twin Refreshed`

## 5. API CONTRACT & VALIDATION

**Standardized API:**
The Digital Twin must expose the following contract to all downstream modules:

* `get_current_state(location_id)`
* `get_historical_state(location_id, time_range)`
* `get_forecast_state(location_id, horizon)`
* `apply_scenario(scenario_parameters)`
* `rollback(version_id)`
* `get_state_history(location_id)`

**Validation & Logging (`logs/twin_engine.log`):**

* Reject updates with missing timestamps, invalid coordinates, duplicate versions, or physically impossible temp/rainfall values.
* Log all state updates, imports, synchronization events, and validation errors.
